# 0.8.0 / 001 — QA task

## 1. Task metadata

| Field | Value |
|---|---|

| Task ID | `001` |
| Owning agent | `qa` |
| Status | `Blocked — waiting for implementation` |
| Depends on | `design/0.8.0/design-decisions.md`, `programmer/0.8.0/CoT.md`, the implementation commits |

| Hands off to | `orchestrator` for integration and acceptance |

## 2. Context

- `0.8.0` removes the three-hit light chain, adds one light attack, and adds a
  numeric depth difficulty curve over the unchanged fixed six-room branch.
- Depth 1 must read as a teaching floor: melee mobs only, the most forgiving
  values on the curve, and no tutorial UI.
- Economy, shop, spirit loop, Warden summon, gate, and descent are unchanged
  from `0.7.0` and are regression surface.
- The previous version's QA found a real cross-floor leak, so descent and
  cross-floor state are a known risk area.

## 3. Objective

Independently verify that the implementation matches the approved product
decisions and the design contract, that the chain is fully gone with no
leftover behavior or configuration, that the depth curve works at depth 1,
across a descent, and at its cap, and that nothing in the `0.7.0` slice
regressed.

## 4. Verification plan

### A. Attack behavior

1. One click performs exactly one swing; holding the button neither repeats
   nor buffers a swing.
2. Windup, active window, recovery, reach, arc, damage, and knockback match
   `design/0.8.0/design-decisions.md`; compare code constants to the document,
   not just to observed behavior.
3. A swing breaks one fragment, and a swing whose arc covers both fragments
   breaks both; the on-screen feedback does not imply a single target.
4. Taking damage still restores every broken fragment on every living mob, and
   a mob killed with an intact fragment still respawns.
5. The player can still dodge, and i-frames still prevent the fragment
   restoration.

### B. Chain removal

1. No chain pips, reply-window pulse, finisher hold, or chain-break effect is
   visible.
2. No chain state exists in the debug snapshot, and no chain type, event, or
   config remains in `src/`.
3. No orphaned stagger configuration or stagger application remains.
4. Confirm the deferred challenge system was **not** partially implemented: no
   challenge card, popup, buff, or new hotkey.

### C. Depth scaling

1. Depth 1 uses the design's teaching values; verify by inspecting the
   generated entities and by playing the floor.
2. Depth 2, reached by defeating the Warden and descending, uses the next row
   of the curve for mobs and the Warden; verify values and observed pressure.
3. Independently compute two or three rows of the curve from the design table
   and confirm the implementation matches, including the cap.
4. Confirm movement speed does not change with depth and that enemy count,
   archetype roster, and floor topology do not change.
5. Confirm the scale is applied to mobs and the Warden generated on the new
   floor, and that no stale values leak from the previous floor.

### D. Composition and teaching floor

1. Depth 1 spawns three melee mobs; depth 2 spawns two melee and one ranged,
   with stable ids and positions.
2. Play depth 1 end to end and judge whether it is forgiving but not inert:
   the player should learn movement, attack, dodge, fragment breaking, and the
   no-damage rite without a tutorial overlay. Record the observed hits-to-rest
   and damage taken.
3. Confirm there is no tutorial prompt, overlay, hint, or tooltip.

### E. Regression matrix (must still work)

- Title screen, boot loading screen, and pause/death screens.
- Spirit meter fill, arena gate unlock, explicit Warden summon, and shop
  closure on summon.
- Shop purchase states for draught and Vigor, draught use, healing caps.
- Stairs open after the Warden dies, descent heals 2 HP and regenerates the
  floor, and per-floor state resets while run state persists.
- Death, run summary, restart with a fresh run, and `R` behavior.
- Audio cues and `M` mute; the game remains playable muted.
- Debug hooks present only under the existing `DEV`/`VITE_E2E` gate.

### F. Quality and documentation

1. `docs/about-the-project.md` matches the delivered behavior: single attack,
   boss uninterruptibility, depth curve, depth-1 composition, flat economy, and
   the deferred challenge direction.
2. No dead code, debug artifacts, or unused exports; no unrelated refactors.
3. Cypress helpers were reworked, not weakened: confirm a retry cannot mask a
   resolved swing.

## 5. Required evidence

- Exact commands run and their results: `npm ci` (clean install),
  `npm run typecheck`, `npm test`, `npm run build`, `npm run e2e`.
- Unit and Cypress test counts, plus three consecutive e2e results to show the
  reworked helpers are stable.
- Canvas captures at 1024 × 640 and 1440 × 810: depth-1 floor with three melee
  mobs, HUD without pips, depth-2 floor with the ranged mob and scaled values,
  Warden fight, and one fragment-break moment.
- The computed-versus-implemented comparison for at least three curve rows.
- A written verdict: `Passed`, `Passed after fixes`, or `Changes requested`,
  with every finding classified as blocking or non-blocking and routed to its
  owner.

## 6. Out of scope

- Judging the deferred challenge system, economy scaling, new archetypes, or
  future dungeon generation.
- Redesigning values chosen by the design agent; if a value is unplayable, file
  a finding against design rather than changing it.
- Fixing the programmer's work silently.

## 7. Constraints

- Verify against the approved sources, not against the implementation's own
  comments.
- Do not accept "it compiles" as evidence.
- Do not run or emulate hosted CI; record GitHub Actions as pending.
- Preserve unrelated user changes and do not rewrite history.

## 8. Acceptance criteria for a pass

1. Every §4 check has a recorded result with evidence.
2. No blocking finding remains open.
3. The regression matrix passes.
4. Documentation matches behavior.
5. The verdict is recorded in `qa/0.8.0/001-report.md` and committed with the
   repository commit format.

## 9. Routing rules

| Finding | Route to |
|---|---|
| Attack, scaling, composition, or chain removal implemented incorrectly | programmer |
| Missing, contradictory, or unplayable numeric values in the design contract | design |
| Product requirement conflict or scope ambiguity | docs/orchestrator |
| Test strategy unable to prove a criterion | docs (task definition), then QA re-verifies |

## 10. Open assumptions / unresolved items

- Unresolved: none. If the design contract is missing a value needed for a
  check, stop that check and route it to design instead of guessing.
