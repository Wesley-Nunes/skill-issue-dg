## 2. Context

- `0.9.0` closes the post-`0.8.0` safe-room exploit and is the last code change
  before the MVP acceptance pass. The MVP acceptance contract now lives in
  `GOAL.md` and uses the agreed interpretations: a seeded fixed six-room topology
  counts as the procedural floor, and shop-only rewards count as the reward
  decision.
- The rule is new behavior layered on the existing shop, enemy aggro, modal
  shop panel, and descent flow. It must not regress `0.7.0` and `0.8.0`
  behavior.
- QA must be independent: reproduce the exploit on the implementation and judge
  it against the task and design contract, not against the programmer's claims.

## 3. Objective

Independently verify that the safe-room combat rule closes the exploit without
trapping the player, weakening the shop flow, or regressing the MVP loop, and
record evidence for the `0.9.0` MVP acceptance gate.

## 4. In scope

1. **Exploit reproduction.** Reproduce the recorded scenarios against the built
   game:
   - lure a melee mob to the shop threshold and try to enter;
   - reproduce the same with the Floor Warden;
   - attack outward from inside while an enemy hunts.
   Record whether each is closed.
2. **Rule correctness.**
   - Entry is refused only while a living enemy hunts.
   - The ward reopens when no living enemy hunts, without a reset.
   - Dying, dead, rested, and emerging enemies do not seal the ward.
   - The player already inside when the ward seals is not trapped and can
     leave.
   - Damage and shop interaction inside the safe zone follow the design
     contract exactly.
3. **Regression coverage.** Verify the existing reward loop still works:
   resting mobs, skill points, draught, Vigor, shop open/close, summon, Warden,
   stairs, descent, death, and restart.
4. **Presentation.** Inspect the sealed and open threshold states, the refusal
   copy, the reduced-motion variant, and that no new HUD element, asset, or
   hotkey appeared. Confirm the feedback is readable with audio muted.
5. **Automated checks.** Run a clean `npm ci`, then `npm run typecheck`,
   `npm test`, `npm run build`, and `npm run e2e` with Chrome; run the e2e suite
   enough times to judge stability. Confirm the production bundle has no
   `__gameDebug` hook.
6. **Release hygiene.** Confirm `README.md` matches the shipped controls and
   loop, and that `package.json`/`package-lock.json` report `0.9.0`.
7. **MVP acceptance evidence.** Execute the loop defined in `GOAL.md` and record
   pass/fail per success criterion, with the evidence used. Do not declare MVP
   completion; report evidence and findings to the orchestrator/operator.

## 5. Out of scope

- Fixing implementation defects. Findings go back to the programmer or design
  owner; QA may add a regression test only when the orchestrator authorizes it.
- Product-scope changes, new features, balance tuning, or design changes.
- Hosted CI and Vercel verification (operator-owned; record as pending).
- Performance, browser-matrix, mobile, or accessibility audits beyond the
  affected states.

## 6. Approved behavior to verify

- A safe room is safe between encounters only; the exploit is closed for mobs
  and the Warden.
- The ward's predicate, entry/exit behavior, protection, interaction rule, copy,
  colours, timing, and cooldown match `design/0.9.0/design-decisions.md`
  exactly.
- No new system, resource, HUD element, asset, audio cue, dependency, or hotkey
  exists.
- `0.8.0` single-attack, purification, depth scaling, and boss behaviour are
  unchanged.

## 7. Constraints

- Verification must be independent of the programmer's decision log; use it for
  intent only, not as proof.
- Prefer observable assertions in the debug snapshot, events, and canvas
  captures over subjective judgment.
- Use the repository Cypress conventions and `cypress/support/` commands.
- Do not modify product code to make a test pass.
- Record any evidence limitation honestly (for example, canvas-only visuals
  without a pixel diff).

## 8. Acceptance criteria

1. Every §4.1 exploit scenario is either confirmed closed or reported as a
   blocking finding with reproduction steps.
2. Every §4.2 rule assertion is verified, including the non-hunting states and
   the already-inside exit.
3. The reward-loop regression pass is completed and recorded.
4. Presentation checks are recorded with exact-size canvas captures for the
   sealed and open threshold states.
5. Clean-install `typecheck`, unit, build, and e2e results are recorded with
   commands, counts, duration, and browser; stability evidence is stated.
6. The production bundle is checked for debug hooks.
7. README and version checks pass.
8. The MVP acceptance table covers every success criterion in `GOAL.md` and
   cites the evidence for each; no criterion is marked passed without evidence.
9. The report records a verdict (`Passed`, `Passed after fixes`, `Failed`) and
   lists every finding with severity, reproduction, and owner.
10. No product code was changed by QA; any added test is explicitly called out.

## 9. Dependencies and handoff

- **Inputs:** the implementation commit, `design/0.9.0/design-decisions.md`,
  `programmer/0.9.0/CoT.md`, `GOAL.md`, and `STATE.md`.
- **Output:** `qa/0.9.0/001-report.md` with evidence, verdict, and findings.
- **Next owner:** orchestrator for review, state update, PR, and operator
  acceptance.

## 10. Open assumptions / unresolved items

- Assumption: "hunting" is observable through the debug snapshot or the pure
  predicate exposed to tests. If it is not observable, that is a blocking
  finding.
- Assumption: the MVP acceptance run may use documented debug setup for
  determinism, but at least one pass must use the normal earn/purchase/summon/
  descend path.
- Hosted CI and deployment remain operator-owned and are recorded as pending,
  not as failures.
- Unresolved: none.
